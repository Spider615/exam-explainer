# ⑤ 提速与后端切换：实测记录

> 2026-08-08。这份文件是**实测数据的存档**，不是设计。所有数字都是跑出来的，
> 每条都注明了样本量。设计与验收在 `2026-08-08-scene-codegen-design.md`。

## 一、时间到底花在哪（这是整轮的起点）

⑤ 一道题（q13）跑一次，用 `claude -p --output-format json` 拿到明细：

| 项 | 数值 |
|---|---|
| 总耗时 | 1322 秒 |
| 纯 API 等待 | 1296 秒（**98%**） |
| 门禁 `verify.py` | 2.1 秒 |
| 拼装 `build.py` | 0.08 秒 |
| **合计确定性部分** | **2.2 秒（0.2%）** |

**⑤ 不是一次长生成，是一个 54 轮的 agent 会话。** 53 次 tool 调用的构成：

| 类别 | 次数 | 明细 |
|---|---|---|
| 探索/导航 | **20** | grep×6、cd×5、ls×4、读别的场景的文件×3、读 `scenegen.py`×1 |
| 验证 | **15** | `verify.py`×12、`build.py`×**3** |
| 真正在写 | **7** | Write×2、Edit×5 |
| 读契约与 spec | 2 | |
| 算参数 | 3 | python3 |

而输出 token 的构成更关键：

| | |
|---|---|
| 会话里可见的产出 | 10,783 字符 ≈ 3,594 token |
| API 报的 output token | **59,971** |
| 差额（thinking，4 个块） | **约 56,000 token（93%）** |

**结论：瓶颈是「轮数 × 每轮思考量」，不是「要写多少字节」。**

这解释了为什么此前两次优化输出量都没换来提速：
砍 47% 的代码量 → 时间没变；换 41% 更小的声明式 → 反而更长。

## 二、两处修好之后（订阅 sonnet）

**修法**：
1. `harness/check.py` —— 把 `build && verify` 合成一条命令。
   原因：agent 只跑后半句，12 次 verify 里至少 9 次验的是没重拼的旧产物。
2. 重写 `BRIEF_CODEGEN` —— 自带完整示例、样式类清单、字宽表，并明写「别翻仓库」。
   原因：它跑去读 `q13-gen6.js` 和 `scenegen.py` 找例子，因为提示词里没给。

**q13 实测（n=1）**：

| | 改前 | 改后 | |
|---|---|---|---|
| tool 轮数 | 54 | **7** | −87% |
| 耗时 | 1322 秒 | **652 秒** | −51% |
| 输出 token | 110,513 | 59,971 | −46% |
| 缓存读入 | 641 万 | 53 万 | −92% |
| 折合费用 | $4.66 | $1.56 | −66% |
| 门禁 | PASS | PASS | |

**再加 `--effort low`**：188 秒、16,327 token、$0.73，**门禁仍然 PASS**。
`claude --effort` 取值：`low / medium / high / xhigh / max`。

## 三、后端切换：方舟

### 模型能力实测

`deepseek-v4-flash-ga-260731`（火山方舟 cn-beijing）：

| 能力 | 结果 |
|---|---|
| 基本对话 | ✅ |
| **函数调用** | ✅ `finish_reason=tool_calls` —— 能驱动 claude CLI |
| **读图** | ❌ `Model do not support image input` |

`doubao-seed-evolving`：读图 ✅（18 秒读出带 LaTeX 的选项），
`.env` 里 `ARK_VISION_MODEL` 本来就是它。

**所以 ②b 公式识别只能用豆包，不能用 DeepSeek。**

### 慢的根因不是垫片

| 排除项 | 证据 |
|---|---|
| 垫片延迟 | 方舟侧 146 秒 / 总 154 秒 —— **垫片只占 5%** |
| prefill | 输入涨 11.9 倍，耗时只涨 1.7 倍 |
| 没有 prompt 缓存 | 重发同样长输入，缓存命中 7680 token、1.5 秒 |

**真因**：DeepSeek-V4-Flash 是推理模型，同一道物理题输出 1774 token 里
**1769 个是 reasoning**。生成速率一直是 ~80 tok/s —— 不是模型慢，是它生成了 6 倍的量。

### 思考预算开关（实测哪些参数有效）

同一道物理题：

| 参数 | 耗时 | 输出 token | reasoning |
|---|---|---|---|
| 不带参数（基线） | 22.4s | 1774 | 1769 |
| **`thinking:{"type":"disabled"}`** | **3.6s** | **286** | **0** |
| `thinking:{"type":"auto"}` | 15.8s | 1241 | 1236 |
| `thinking:{"type":"enabled","budget_tokens":256}` | 16.5s | 1324 | 1319（**budget 被忽略**） |
| `reasoning_effort:"low"` | 34.2s | 2564 | 2559（**更慢**） |
| `reasoning_effort:"minimal"` | 1.4s | 19 | 0（答案不完整） |

**只有 `thinking:{"type":"disabled"}` 管用。** 关掉之后答案照样对
（推导写进可见输出，实测斜面题两者都给出 3.58 m/s）。

已在 `pipeline/arkshim.py` 加开关：环境变量 `EXAM_ARK_THINKING=disabled`。
默认不传这个字段，保持模型默认 —— 不设就跟以前一模一样。

### ⑤ 在方舟上的实测（每格 n=1，全部 PASS）

| 题 | 开思考 | **关思考** |
|---|---|---|
| q4（简单） | 154 秒 / 11,426 tok | **65 秒 / 4,416 tok** |
| q13（复杂） | 1142 秒 / 10,317 tok | **434 秒 / 33,605 tok** |

**关思考在复杂题上没有掉链子** —— L5 24 条文字零重叠、L4 18/18。
这是这个方案里最主要的风险，已经兜住。

## 五、要落的配置

| 阶段 | 走哪 | 思考 | 理由 |

## 六、保留意见（每一条都要记住）

1. **全部是 n=1。** 每个配置每道题只跑了一次，模型有随机性。
2. **④ 关思考没验过。** 上表让它保持开思考是**推断**，不是实测 ——
   ④ 写错 spec 的话下游全废，落地前应该单独验。
3. **`.env` 里那句注释是错的**：写着 `ARK_API_KEY` 与 `EXAM_SCENE_ARK_KEY`
   属于不同账号，实测**两个 key 完全相同**。
4. **`arkshim.ensure()` 发现端口已占就直接复用**，不检查那个垫片是谁起的、
   用什么 key。key 一变会静默发到旧账号，而且没有任何提示。**这是个隐患。**
5. `--effort low` 在订阅上也只验过 q13 一道。
