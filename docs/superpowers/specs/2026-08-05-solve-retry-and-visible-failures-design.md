# 解题重试与失败原因展示设计

## 背景

阶段③当前会把单题异常变成一条日志后继续处理整卷。成功答案会写入 `solutions`，失败题却没有持久化记录；任务进程结束后，页面只能看到“解题 14/15 · 已停止”，无法区分尚未执行、请求超时和模型返回异常。

现有 HTTP 调用虽设置了 300 秒 socket 超时和内部重试，但它不是单题完整生成的硬截止时间，也没有可靠终止仍在等待的调用。此次改动同时解决自动恢复和失败可见性。

## 目标

- 单道题的一次完整生成最多运行 5 分钟。
- 包含首次尝试在内，每题最多尝试 3 次；失败后间隔数秒再建立全新请求。
- 第 3 次仍失败时，将失败类型、可读原因和实际尝试次数持久化。
- 试卷列表、试卷详情顶部和对应题目都能看到失败状态；刷新页面或服务重启后仍然存在。
- 后续重新生成成功时，自动清除旧失败记录。

## 非目标

- 不为阶段④到⑦增加同类重试。
- 不保存完整异常堆栈、模型响应或请求载荷到产品数据库。
- 不在本次改动中增加手动“重试此题”按钮；重新运行阶段③仍沿用现有入口。
- 不改变答案质量判断、交叉复核或动画选择策略。

## 方案选择

采用独立的 `solution_failures` 表保存每道题当前一次终态失败。它与 `solutions` 一样以 `question_id` 为主键，但只表示失败，不把成功和失败两种含义混进同一行。

未采用的方案：

- 只记录到任务内存或日志：服务重启后丢失，页面无法可靠查询。
- 给 `solutions` 增加 nullable 失败字段：没有成功答案时仍要伪造一行 solution，容易让下游把失败当成已有答案。

## 解题执行与硬超时

`solve_many` 仍按题并行，但每一次 `solve_one` 在独立子进程中执行。父进程按 300 秒等待：

1. 子进程在时限内成功，沿用现有逻辑写入答案并返回成功。
2. 子进程返回异常，父进程记录本次错误，等待短暂退避后重试。
3. 子进程超过 300 秒，父进程终止其进程组，避免视觉模型或 CLI 子进程遗留，再开始下一次尝试。
4. 最多执行 3 次。第 3 次失败后，父进程写入终态失败记录并继续处理其他题目。

每次重试都启动新进程和新连接。重试边界包住完整的单题生成链路，因此 DeepSeek 盲试、视觉模型升级和答案落库合计都受同一个 5 分钟上限约束。单题最坏等待约 15 分钟，另加两次很短的退避时间。

开始新一轮生成时先清除该题旧失败记录；写入成功答案时在同一数据库事务中再次清除失败记录。即使之前失败过，成功状态也不会与失败状态并存。

## 失败分类与数据模型

新增表字段：

- `question_id`：题目主键，也是本表主键。
- `kind`：稳定的机器分类，如 `timeout`、`network`、`provider`、`invalid_response`、`configuration`、`internal`。
- `reason`：供用户阅读的中文原因，限制长度并移除潜在敏感内容。
- `attempts`：实际尝试次数，正常终态失败为 3；不可启动的本地配置错误可以提前结束。
- `stage`：失败发生在文本模型、视觉模型、交叉复核之外的主流程或未知阶段。
- `created_at`、`updated_at`：首次和最近失败时间。

页面只展示归一化后的原因，例如：

- `视觉模型请求超时（单次超过 5 分钟），已尝试 3 次。`
- `模型服务暂时拒绝请求（HTTP 429），已尝试 3 次。`
- `模型返回内容无法解析为答案，已尝试 3 次。`

原始异常只进入受控任务日志并截断；不得把密钥、Authorization 头、base64 图片或完整上游响应返回给前端。

## 进度与 API 语义

进度查询新增失败题计数。阶段③的完成量改为：

`成功答案数 + 终态失败数`

因此 14 道成功、1 道经过三次尝试后失败的试卷会结束阶段③并继续执行后续阶段，不再永久显示为“14/15 已停止”。下游仍只以成功答案为输入，失败题不会进入断言或动画生成。

整卷可以在有失败题时完成，但状态必须表达为“已完成 · 1 题失败”，而不是无条件显示成功。完整试卷接口为每题增加可空的 `solutionFailure`，包含 `kind`、`reason`、`attempts`、`stage` 和更新时间；进度及列表接口增加失败总数。

## 页面行为

- 试卷列表：有终态失败时显示“已完成 · 1 题失败”，避免误认为整卷全部成功。
- 试卷详情顶部：显示常驻红色提示，列出失败题号和简短原因；点击题号跳到对应题目。
- 答案速览和目录：失败题显示失败标记，不再写“尚未生成”。
- 题目卡片：在“解题思路”位置显示“生成失败”、原因、尝试次数及最近失败时间。
- 真正尚未跑到阶段③的题目仍显示“尚未生成”，两种状态严格区分。
- 轮询键加入失败计数，使失败记录落库后页面自动重新拉取整卷，无需手动刷新。

## 一致性与异常恢复

- 失败记录与成功答案互斥；成功写入时事务内删除失败记录。
- 新一次主动生成开始时删除旧失败，运行期间页面依赖现有 `busy`/`step` 展示正在重试。
- 父进程意外退出时，已经落库的成功答案保留；只有完成全部尝试的题才写终态失败。
- 子进程超时后先温和终止，短暂等待后仍未退出则强制结束进程组，防止后台请求泄漏。

## 测试与验收

后端先写失败测试，再实现：

- 前两次超时、第三次成功时共执行 3 次，只留下成功答案，不留下失败记录。
- 连续 3 次超时时写入 `timeout` 失败，`attempts=3`，并继续处理其他题。
- 非超时的请求异常同样受最多 3 次限制；不可重试的配置错误不会浪费三次远端等待。
- 单次运行超过测试用短时限时会被终止，子进程不会继续落库。
- `stage_of` 把成功数与终态失败数相加计算阶段③进度，下游分母仍只使用成功答案数。
- 试卷 API 给失败题返回 `solutionFailure`，成功题返回 `null`。
- 成功写入会清除既有失败记录。

前端通过 TypeScript/Vite 构建，并人工验证三种页面状态：生成中、三次失败、失败后重新生成成功。最终对当前第15题做一次受控重跑，确认页面能自动显示重试结果或明确失败原因。
